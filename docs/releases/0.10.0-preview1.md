# WindowsDeviceLink 0.10.0-preview1

This consolidation preview formalizes two execution routes without splitting the module:

- **Direct mode** talks directly to Microsoft Graph. Interactive and DeviceCode flows do
  not require TenantId; the sign-in context chooses the tenant. An explicit tenant or a
  friendly-name JSON catalog remains available when an operator manages several tenants.
- **Backend mode** uses the optional Azure Function backend for an authenticated tenant
  catalog, complete multitenant lookup, and guarded New, no-op, or Move orchestration.

## Unified assignment

`Set-WindowsDeviceLinkTenant` now supports both routes. Direct mode reuses the safe
initializer and one authentication context. Backend mode retains full pre/post-state
verification and never silently falls back to Direct mode.

Assignment results expose `OperationMode`, `Decision`, `ReasonCode`, `Changed`,
`RetrySafe`, and `RecommendedAction` alongside tenant and association details.

## Operator GUI

The unified operator view exposes Device, Connection, Local association, and Cloud
association in a compact two-by-two layout, with all actions below. In Backend mode, the operator selects a target tenant and
**Pre-register** performs lookup, decision, identity renewal, registration, and
verification as one workflow. **Full register** continues with device-side completion on supported full Windows. Direct mode displays whether the tenant is determined by
sign-in or selected explicitly. Backend mode requires an explicit target from the
authenticated Function catalog. Diagnostic and lifecycle controls remain available in
the same view.

The GUI opens without authentication in Direct mode and loads local state first. An
explicit **Sign in** action authenticates once, loads the cloud association, and reuses
the in-memory session for subsequent cloud actions. Selecting another tenant invalidates
that session. Backend mode still loads cloud state automatically because it does not
require an interactive Graph sign-in on the device. Status cards use subtle,
non-exclusive color cues while retaining explicit text labels. The packaged application
icon and WinPE-safe font fallback do not depend on organization branding.

After authentication, **Sign in** becomes **Switch account**. Direct single-tenant mode
does not show a tenant selector. A configured local tenant catalog does show the selector
and requires an explicit target before authentication or registration; changing the
target clears the current GUI session.

## Validation

Release validation is tracked in [`../TEST-MATRIX-0.10.0.md`](../TEST-MATRIX-0.10.0.md).
The matrix treats operator-friendly CLI use and predictable non-interactive automation
as separate release requirements, alongside the GUI authentication routes.

The Backend-mode workflow was validated from Windows PE with a real device across two
configured tenants. New/no-op and verified Move behavior were exercised, including a
successful bidirectional tenant reassignment after local identity renewal. Automated
contract, backend-runtime, tenant-assignment, authentication, transport, and safety
regressions remain part of CI.

Physical end-to-end validation also covered the complete production-shaped lifecycle:

- WinPE pre-registration using the Bring Your Own DLL (BYO-DLL) compatibility path;
- Windows 11 OOBE automatically changing the tenant record from pre-associated to associated;
- local firmware changing from `2/4` base identity to `4/4` full association;
- an explicitly assigned Device Preparation policy taking precedence;
- successful Intune enrollment after organizational sign-in.

Windows 11 25H2 build `26200.9168` did not enter the Device Association OOBE path in this validation. After servicing to build `26200.9457` with `KB5129195`, the same physical device completed the flow successfully. Deployment media should use current cumulative updates; this observation isn't intended to pin the workflow permanently to one KB.

For this preview, the supported backend delivery route is the supplied Function App
package with documented manual Azure configuration. The Bicep/ARM deployment remains
experimental while the public Deploy to Azure experience is hardened and validated
separately.

## Backend compatibility

The tenant-catalog endpoint now returns API version, minimum module version, and
capabilities. Version or capability mismatches fail closed before any cloud mutation.

## Tenant catalogs

`Get-WindowsDeviceLinkTenantCatalog` reads a local JSON file, trusted HTTPS JSON, or
hashtable. A catalog is an address book only: it does not provide cross-tenant lookup or
Move capability.
