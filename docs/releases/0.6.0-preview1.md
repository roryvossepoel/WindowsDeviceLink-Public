# WindowsDeviceLink 0.6.0-preview1

This preview expands WindowsDeviceLink from registration/completion tooling into a more complete Device Association lifecycle toolkit, with explicit offboarding guidance, simpler authentication UX, safer cloud-response handling, and multitenant reconciliation support in the reference Azure backends.

## What's new

### Offboarding lifecycle

- Added a dedicated offboarding guide.
- Documented the difference between **Pre-associated** and **Associated** devices.
- Added lifecycle diagrams for registration, association, offboarding, firmware state and tenant moves.
- Clarified that an associated device requires both local DeviceLink firmware cleanup and tenant-side Device Association removal.
- Clarified that classic Autopilot registration is a separate lifecycle object.

### Simpler authentication and targeting

- `Interactive` authentication no longer requires `TenantId` when the sign-in context can determine the tenant.
- Native `DeviceCode` can omit `TenantId` and defaults to the Microsoft identity platform `organizations` authority.
- Caller-supplied `AccessToken` can omit `TenantId`; the token `tid` claim is resolved on a best-effort basis for metadata and correlation.
- App-only client-secret and certificate methods remain explicitly tenant-specific.
- `-Method` remains explicit and benefits from PowerShell tab completion through `ValidateSet`.

### Local-device removal UX

`Remove-WindowsDeviceLinkAssociation` now defaults to the current physical device when neither `-SerialNumber` nor `-AssociationId` is supplied.

The cmdlet:

1. reads the local BIOS serial number;
2. reports the automatically selected serial;
3. resolves the matching tenant-side Device Association;
4. performs the existing guarded removal operation.

Explicit serial-number and association-ID targeting remain available.

### Hardened Graph collection handling

Live testing exposed Microsoft Graph SDK response-shape differences under PowerShell 7.

The collection helper now supports:

- normal PowerShell object responses;
- dictionary-shaped SDK responses;
- explicitly present `value = $null` as an empty collection;
- continued fail-closed behavior when the required `value` key is missing.

Regression coverage was added for these response variants.

### Multitenant reconcile reference workflow

The Azure Function and Azure Automation reference backends now include a controlled **New / Move / Update** reconciliation model.

```text
not found anywhere -> New
found in target     -> Update
found elsewhere     -> Move
```

The backend performs a fresh lookup before every state-changing decision.

A Move requires:

- exactly one detected source association;
- an explicitly matching `sourceTenantId`;
- re-reading the source immediately before deletion;
- verifying source absence;
- verifying the target is still empty;
- creating the target pre-association;
- verifying the resulting target association.

There is intentionally no standalone public DELETE endpoint.

See [RECONCILE-SCHEMA-v1.md](../RECONCILE-SCHEMA-v1.md).

## Live lifecycle validation

Validated on a physical Microsoft Surface Laptop 3 running AMD64 Windows 11.

An associated device started with all four known DeviceLink UEFI variables present.

The offboarding test then:

1. reset all four local DeviceLink UEFI variables;
2. immediately verified firmware state `0/4`;
3. removed the tenant-side Device Association using `Remove-WindowsDeviceLinkAssociation -Method Interactive` with automatic local serial-number detection;
4. verified that no tenant-side Device Association remained;
5. rebooted the device and confirmed firmware still remained `0/4`;
6. invoked `Get-WindowsDeviceLink`;
7. confirmed that a new base identity was materialized as `2/4` (`DeviceLinkId` and `DeviceLinkCreationTimeUtc` only).

This refines the previously observed lifecycle behavior: a reboot alone does not necessarily recreate the base DeviceLink identity. A later DeviceLink identity retrieval can materialize a new base identity.

## Safety boundaries

This release keeps the existing safety model:

- no automatic firmware reset during cloud operations;
- no automatic local cleanup during multitenant reconcile;
- no blind retries of DELETE/POST mutations after uncertain transport failures;
- no raw DeviceLink or association JWT logging;
- no automatic cross-tenant admin consent;
- no classic Autopilot registration deletion through Device Association cmdlets;
- native device-side completion remains explicit opt-in.

## Notes

WindowsDeviceLink remains preview / proof-of-concept software. Native DeviceLink completion uses undocumented Windows Runtime interfaces, and Device Association cloud operations use Microsoft Graph beta endpoints. These interfaces can change without notice.
